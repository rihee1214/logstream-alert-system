# Planned - Biz Service

## [ ] SPAN_ID 생성 로직 개선

- **문제 요약**: 기존의 SPAN_ID는 16자리의 자동 생성된 hex 문자열을 사용하고 있음. 이는 시스템 간 추적성 확보에는 적합하지만, 사람의 인지성을 떨어뜨리고 로그만으로는 어떤 서비스에서 생성된 span인지 파악하기 어려움.
- **핵심 영향**: 구조화 로그 또는 추적 시스템에서 span 구간을 눈으로 구분하거나 빠르게 필터링하기 어려움
- **고려했던 대안**:
  1. **서비스명을 SPAN_ID에 포함시켜 식별성을 강화**
     - 예: `log-biz-f4e1a3b7a1d2e59c` 또는 `f4e1a3b7a1d2e59c-biz`
     - 장점: 사람이 볼 때 서비스 위치 추적 용이
     - 단점: SPAN_ID의 길이 증가, 고정 길이 파싱 어려움, Zipkin 호환성 저하
  2. **기존 형식을 유지하고 서비스명을 별도 필드에 유지**
     - 예: SPAN_ID는 `f4e1a3b7a1d2e59c` 유지, 로그 필드에 `service.name = log-biz` 추가
     - 장점: 쿼리 효율 우수, 추적 도구 호환성 유지, 로그에서 필드 기반 추적 가능
     - 단점: 로그를 통해 한눈에 span 소스를 알기 어렵고 시각화 도구 필요
- **결론 및 우선 방안**:
  - SPAN_ID는 기존의 64비트 hex 형식(예: `f4e1a3b7a1d2e59c`) 그대로 유지
  - 로그 메시지에는 `service.name`, `component`, `log_type` 등의 식별 필드를 반드시 포함시켜 추적 가능하게 함
  - 필요 시 사용자 정의 식별자(`operationId`, `label`, `stepId`)를 별도 필드로 도입하여 시인성을 보완

## [ ] MDC 전파 구조 반영

- **문제 요약**: WebClient 응답 처리나 예외 처리처럼 새로운 스레드에서 로직이 수행될 경우, `traceId`, `spanId`, `parentSpanId`가 MDC에서 사라져 추적 불가 상태가 됨
- **핵심 영향**: biz 로그에서 traceability 상실 → 시스템 연계 흐름 파악 불가
- **해결 방안**:
	1. **MDCContextHolder와 유사한 구조의 Bean 강제 주입**
	     - 장점: 프레임워크 차원의 해결 시도
	     - 단점: 실수로 미사용 시 추적 불가, 언어 차원에서 강제 불가능
	2. **테스트 기반 검증 및 책임 전가**
	     - 장점: 개발 책임자 중심 운영
	     - 단점: 테스트 비용 과다, 자동화 불가
	3. **MDC 누락 시 SYS 로그로 에러 강제 기록 + 알림 연동**
	     - 장점: 장애 조기 감지 가능
	     - 단점: 알람 폭주 가능성, 원인 추적의 어려움

## [ ] 분산 시스템에서 추적 헤더 자동 적용 반영

- **목표**: HTTP 요청 시 `traceId`, `spanId`, `parentSpanId`가 자동으로 헤더에 삽입되도록 하여 전 구간 추적 가능하게 만들기
- **해결 방안**:
	- WebClient/RestTemplate에 interceptor 또는 filter 형태로 삽입
	- 지연 평가(lazy eval) 구조로 처리하여 context 전파 시점 유연성 확보
