## 1. 주제(Title)

비즈니스 로그 저장 및 추적을 위한 DB 선택

---

## 2. 문제 인식(Problem Recognition)

중·대규모 플랫폼을 위한 로그 저장소를 선택함에 있어 기존의 EFK(Easticsearch-Filebeat-Kibana) 조합은 운영 복잡성과 비용 문제로 적합하지 않다.  
특히 E, 즉 Elasticsearch는 장기 보존, 정합성, 확장성에서 점차 **부적합한 솔루션**으로 평가된다.

이번 검토는 단순한 저장소 변경이 아닌, **플랫폼 전체 아키텍처를 재구성하는 수준의 결정**이며, 이에 따라 다음과 같은 조건을 기준으로 DB를 재검토하였다:

- 대용량 로그 처리 및 장기 저장
- 추적 기반 조회(traceId, spanId, service 등)
- 최종적 일관성 허용
- 가용성 중심
- 클라우드 및 온프레미스 유연성
- 지속 가능한 운영과 확장 전략

---

## 3. 고려사항(Considerations)

- **Option 1: Elasticsearch**
	- 장점
		- 자유로운 쿼리 및 시각화 도구(Grafana, Kibana 등)와의 강력한 통합
	- 단점
		- 고비용 구조 (JVM 기반 + 고사양 필요)
		- 클러스터 샤딩 및 노드 운영 복잡도 높음
		- 대량 데이터 처리 시 성능 저하 및 관리 이슈 발생
		- 복잡한 분석 기능을 위한 **내부 처리 로직(JVM GC, 인덱싱 등)** 으로 리소스 과다 사용

- **Option 2: Cassandra**
	- **장점**
	    - 분산형, AP 지향 구조 → 수평 확장 및 고가용성에 적합
	    - 고성능 쓰기 처리, 대용량 데이터 처리 능력 우수
	- **단점**
	    - 정형화된 쿼리 패턴 요구 → 유연한 로그 조회 어려움
	    - 스키마 고정 구조로 유연한 필드 확장 어려움
	    - MDC 기반 필드의 자유 확장 시 충돌/관리 이슈 가능

- **Option 3: ScyllaDB**
	- 장점
		- Cassandra의 완전한 대안으로, **더 낮은 지연시간**과 **고성능 처리 가능**
		- 분산형, AP 지향 구조 → 고가용성 및 수평 확장성 우수
		- 자체 스케줄링 기반 리소스 최적화
		- Materialized View(MV)를 통한 병렬 조회 패턴 구성 가능
	- 단점
		- 정형화된 쿼리 패턴 요구 → 유연성 낮음
		- MDC 기반 필드 확장 시 스키마 관리 이슈 존재
		- MV는 eventual consistency 기반 → **운영 전략 및 정책 필요**

- **Option 4: ClickHouse**
	- 장점
		- 초고속 OLAP(Online Analytical Processing) 쿼리에 강점
		- 대량 데이터의 columnar 저장 최적화
		- 대규모 집계, 트렌드 분석에 적합
	- 단점
		- 로그의 단건 조회(예: traceId 단위 추적)에 부적합
		- 실시간 쓰기 성능은 제한적이며, **OLTP 목적에는 부적절**
		- Cassandra/Scylla처럼 분산 쓰기 기반 아키텍처가 아님
		- **본 프로젝트의 핵심 요구사항(추적, 단건성, 실시간성)에 비해 OLAP 특화 아키텍처는 과도한 기능과 구조적 복잡성**을 유발할 수 있음

- **Option 5: DynamoDB**
	- 장점
		- AWS 완전 관리형 NoSQL 서비스
		- 자동 확장, 고가용성 보장
		- 낮은 지연 시간의 key-value 접근에 매우 효율적
	- 단점
		- **AWS 종속성**이 강하며, 온프레미스/멀티 클라우드 전략에 제약
		- 스토리지 용량 및 요청 단가가 비즈니스 로그 대량 저장에는 비효율적
		- 복잡한 secondary index 구성이 제한적이고 유지비용이 큼

- **Option 6: MongoDB**
	- 장점
		- 유연한 스키마 구조로 다양한 로그 형태 수용 가능
		- 복잡한 중첩 JSON 구조 저장 및 조회에 적합
		- 개발자 친화적 쿼리 및 풍부한 라이브러리 생태계
	- 단점
		- 대량 쓰기/읽기에서 **스케일 성능이 Cassandra/Scylla에 비해 성능상 한계 존재**
		- TTL이나 expire 기반 로그 관리 정책이 복잡함
		- BSON 기반 저장으로 인해 불필요한 필드까지 디스크 사용 → 비효율
		- 안정적인 클러스터 운영을 위해 많은 운영 노하우 요구됨

---

## 4. 최종 결정(Final Decision)

**ScyllaDB를 비즈니스 로그 저장소로 채택한다.**

- **Cassandra 호환 구조 기반**으로, 쓰기 지연을 줄이기 위한 **C++ 기반 비동기 스케줄링 엔진(Seastar)** 을 통해 고성능 보장
- **정형화된 로그 구조**에 맞춰 효율적인 **Base Table + Materialized View(MV)** 구조로 설계 가능
- 추적 로그용으로 많이 사용되는 `(traceId, spanId)` 단건 조회, `operationId`, `timestamp` 기반 병렬 조회에 최적
- **장기 저장**, **높은 쓰기 처리량**, **수평 확장**, **운영 효율성** 모두 충족
- Elasticsearch 제거 및 Kibana 폐지로, **운영 복잡도 및 리소스 비용을 대폭 절감**

---

## 5. 기대효과(Expected Benefits)

- **대량 쓰기 처리 및 장기 보존에 강한 분산 구조**로 안정적인 로그 인프라 확보
- 정형화된 PK 설계 기반의 **안정적인 추적 로그 성능**
- **MV 기반 읽기 분산**으로 병목 최소화
- 불변 데이터 기반의 운영으로 **eventual consistency 전략 수립 가능**
- **ElasticSearch 제거로 인한 비용 절감 및 운영 부담 완화**

---

## 6. 계속 고민할 사항(Still Open Issues)

- MDC 확장 정책 결정 → **스키마 고정 구조**로 인해 사전 조율 필요
- MV miss 시 fallback 조회 방식 설계 필요 → **캐시 전략 vs Base Table 병렬 조회**
- Trace 성능 vs 유연성 트레이드오프 지속 평가
- 고급 쿼리 또는 통계/알람 기능은 Monitoring 서비스가 직접 담당해야 함
- 백업 및 복제 전략 (노드 간 read repair, MV backfill) 자동화 필요
