## 1. 주제(Title)

설정값 검증 책임을 사용하는 Bean 단위로 위임할 것인가?

---

## 2. 문제 인식(Problem Recognition)

개발이 진행되면서 외부에서 주입받는 설정 값(property)의 수가 점점 늘어나게 되었고,  
이러한 설정 값들의 유효성을 사전에 검증하지 않으면 예기치 못한 런타임 오류나  
로그 누락 등의 문제가 발생할 수 있다는 점을 깨달았다.

안정적인 로그 수집과 서비스 동작을 보장하기 위해,  
모든 설정 값을 기동 시점에 검증하는 구조가 필요하다고 판단되었고,  
이를 위해 다음 두 가지 방식 중 어떤 접근이 적절할지 고민하게 되었다:

- 하나의 공통 Bean 또는 설정 전용 구성 요소에서 모든 설정 값을 일괄적으로 검증할 것인가?
- 아니면, 각 설정을 실제 사용하는 Bean 내부에서 개별적으로 검증하도록 책임을 분리할 것인가?

---

## 3. 고려사항(Considerations)

- **Option 1: 설정 검증을 공통 Bean 또는 설정 정의 전용 Bean에서 수행**
	- 장점:
	    - 설정 전체를 한곳에서 빠르게 검토 가능
	    - 빠른 설정 누락 탐지가 가능
	- 단점:
	    - 설정과 사용 위치가 분리되어 유지보수 난이도 증가
	    - 사용되지 않는 설정이 남아도 검증이 남아 있음
	    - 설정 제거와 검증 제거의 연동이 어려움

- **Option 2: 설정을 실제 사용하는 Bean에서 검증 (권장안)**
	- 장점:
	    - 검증 책임이 명확하게 귀속됨
	    - 설정이 제거되면 검증도 자연스럽게 함께 제거됨
	    - 설정 흐름 추적 및 유지보수성 향상
	- 단점:
	    - 매번 `@PostConstruct` 등을 사용해 개별 Bean마다 검증 코드 작성 필요
	    - 전체 설정 목록 파악은 다소 어려움

---

## 4. 최종 결정(Final Decision)

**Option 2를 선택한다.**

- 모든 설정 값에 대한 검증 책임은 해당 설정을 실제로 사용하는 Bean 내부에 둔다.
- 설정 정의용 Bean, 공통 Bean 등에서는 설정 검증을 하지 않는다.
- 각 Bean은 `@PostConstruct` 또는 생성자 수준에서 설정 유효성 검사를 수행해야 한다.
- 이 원칙은 개발 가이드에 명문화하여 관례로 유지하며, PR 리뷰 기준에도 반영한다.

---

## 5. 기대효과(Expected Benefits)

- 설정 사용 여부와 검증 책임이 일치하여 유지보수가 쉬워진다.
- 사용하지 않는 설정이나 검증 코드가 남아 코드 오염이 발생할 가능성을 제거할 수 있다.
- 설정 추가·삭제가 자연스럽게 검증 로직과 동기화되며, 구조 정합성이 향상된다.

---
