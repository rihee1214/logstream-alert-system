## 1. 주제(Title)

`@EnableWebSecurity` 선언 위치에 대한 구조적 방침

---

## 2. 문제 인식(Problem Recognition)

Spring Boot는 보안 관련 자동 구성을 기본으로 제공하며,  
`@EnableWebSecurity`를 선언하는 순간 해당 자동 구성이 비활성화되고,  
직접 명시한 보안 설정만 적용된다.

이 어노테이션은 선언 위치에 따라 전체 서비스의 보안 초기화 방식에 영향을 미치며,  
특히 공통 Bean이나 설정 정의 위치에 선언될 경우,  
의도하지 않게 다른 서비스의 보안 흐름까지 간섭할 수 있다.

보안 책임이 모듈마다 다르고, 서비스마다 보안을 어떻게 구성할지는 자율성에 따라 달라지기 때문에  
`@EnableWebSecurity` 선언 위치에 대한 구조적 기준을 명확히 해야 할 필요가 있다.

---

## 3. 고려사항(Considerations)

- **Option 1: 공통 Bean 또는 공용 보안 설정 클래스에서 선언**
	- 장점:
	    - 선언 위치를 고정할 수 있어 일관성 있음
	    - 전체 서비스에 동일한 보안 구조를 강제 가능
	- 단점:
	    - 모든 서비스에 동일한 보안이 적용되어 확장성 저하
	    - mock/test 서비스에도 보안 필터가 적용되는 등 부작용 발생
	    - 각 서비스가 자체적인 보안 구성 주도권을 잃게 됨

- **Option 2: 선언을 하지 않으며, 각 서비스가 자율적으로 판단하여 선언 여부 결정**
	- 장점:
	    - 보안 구성을 명확히 사용 서비스에서 주도할 수 있음
	    - 공통 Bean의 간섭이 없어 테스트/모의 서비스에 유리
	    - 서비스 간 책임 분리 구조 유지
	- 단점:
	    - 선언 누락에 의한 자동 구성 적용 여부 인지가 어려울 수 있음
	    - 실수로 다수 선언 시 런타임 충돌 가능

---

## 4. 최종 결정(Final Decision)

- `common` 또는 공통 Bean에서는 `@EnableWebSecurity`를 선언하지 않는다.
- 보안이 필요한 서비스(`biz`, `alerting`, `admin` 등)는  
  **자신의 판단과 책임 하에 `@EnableWebSecurity`를 선언**한다.
- 선언 여부는 중앙에서 강제하지 않으며,  
  보안 구조는 서비스별로 자율 구성하는 구조를 채택한다.

---

## 5. 기대효과(Expected Benefits)

- 각 서비스가 보안 구성을 직접 선택하고 제어할 수 있음
- 공통 설정이 보안을 간섭하지 않음으로써 테스트/모의 서비스 구성 유연성 증가
- 선언 위치가 구조적으로 명확해져, 유지보수 시 실수 방지

---

## 6. 계속 고민할 사항(Still Open Issues)

- 보안 구성 통합이 필요한 경우, 추후 다시 선언 위치를 중앙화하는 방식 검토
- 다수 선언 시 충돌 가능성에 대한 경고 체계 필요
- 보안 설정 변경 시 서비스 간 구조 일관성 유지 방안 고민

# ✨ 추가 확장 항목 (Optional)

## 대안 방안(Alternative Options)

- 공통 영역에 선언하고, 서비스별로 `SecurityFilterChain`만 개별 정의하는 구조
	- 서비스 분리를 명확히 할 수 없으며, 테스트 환경에서 예상치 못한 보안 필터 적용 가능성 있음
	- 보안 책임이 어디에 있는지 추적하기 어려움
## 리스크 및 대응(Risks & Mitigation)

- 실수로 여러 곳에 선언할 경우 충돌 가능
	- 개발 가이드에 선언 위치 방침 명문화
	- 코드 리뷰 시 선언 중복 여부 확인
	- 단일 선언 여부를 CI로 확인하는 검사 스크립트 도입 고려

## 추후 개선 방향(Future Improvements)

- 운영 보안 정책에 따라 보안 구성을 통합하거나 중앙화할 가능성 존재
- `security-core`와 같은 별도 보안 모듈을 도입해 선언 위치를 명시적으로 분리할 수 있음
