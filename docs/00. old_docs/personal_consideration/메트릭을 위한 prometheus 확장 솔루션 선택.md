# Prometheus 확장 솔루션 선택

## 🔍 1. Thanos

### ✅ 장점

- Prometheus **원형 그대로 유지**하면서 수평 확장 + 장기 저장
- 객체 저장소(S3, GCS 등)에 WAL/TSDB 업로드하여 장기 보존
- Grafana, PromQL 완벽 호환
- **운영 난이도 가장 낮고**, 실제 기업 도입 사례 가장 많음

### ⚠️ 단점

- **Prometheus를 직접 운영해야 함**
- AlertManager를 각 인스턴스마다 따로 둬야 함 (Sharding 필요)
- 멀티 테넌시가 미약함 (별도 테넌시 구분 로직 필요)


---

## 🔍 2. Mimir

> Cortex의 설계 유산을 개선하고, 실전 운영을 단순화한 "Cortex 2.0"

### ✅ 장점

- **Cortex보다 가볍고 효율적**, 작게 시작해서 확장 가능
- Prometheus 기반 구조 유지 + 멀티 테넌시 강함
- Grafana Labs에서 관리하며, **업데이트와 통합이 빠름**
- 리더리스 구조 / Blob Storage 저장

### ⚠️ 단점

- **기업 수준으로 가기엔 아직 신생 느낌** (운영 자료, 사례는 점점 늘고 있음)
- 일부 기능은 Thanos보다 미완성된 부분도 있음 (복잡한 alert routing 등)

---

## 🔍 번외. Cortex

### ✅ 장점

- Cortex는 원래 **멀티 테넌시 + 수평 확장**을 강하게 고려한 구조
- Loki(로그), Tempo(트레이싱)와 같은 Grafana 제품들과 **구조적으로 통일**
- **기업 내 여러 팀을 위한 플랫폼화**에 적합

### ⚠️ 단점

- 구성 요소가 너무 많음 (ingester, querier, distributor, etc.)
- DynamoDB, Cassandra, Bigtable 같은 **NoSQL 백엔드 필요**
- **설정이 까다롭고, 버전간 호환 문제**도 간혹 발생
- **추후 해당 설계를 이어 받은 것이 Mimir임**

## ## 결론

### 📌 설계 의도 및 검토 목적

- 지금까지 도입한 프로젝트에 들어가는 모든 솔루션들이 **현재 요구사항에 비해 과하거나 부적절한 측면**이 없는지 점검
- **보다 효율적인 대체제 존재 여부를 검증**하고, 장기적인 유지보수성과 운영 효율성을 함께 고려함
- 단순히 동작하는 것이 아닌, **비즈니스 아키텍처 전체 맥락에서 가장 합리적인 도구인지 판단**하고자 했음
- 해당 프로젝트는 **중~대규모 시스템의 기반 플랫폼 역할을 수행**해야 하며, **장기적인 안정성과 운영 비용**까지 감안한 솔루션 선택이 필수였음
### ✅ 최종 선택: Thanos

### 🔍 선정 사유 요약

1. **접근성과 운영 용이성**
     - Thanos는 문서화가 잘 되어 있으며, 커뮤니티와 사례도 풍부하여 학습 장벽이 낮음
     - 구성 요소 간 역할이 명확하고 운영 난이도가 비교적 낮음
2. **저장소 유연성과 관리 부담 감소**
    - Mimir는 직접 NoSQL 기반 저장소 운영이 필요하지만, Thanos는 S3 등 **객체 저장소만으로도 운영이 가능**
    - AWS S3뿐만 아니라 **온프레미스 객체 스토리지(MinIO 등)**도 지원하여 클라우드 종속성이 낮음
3. **멀티 테넌시 불필요성**
    - 본 프로젝트는 **B2B SaaS 형태의 멀티 테넌시 플랫폼**이 아니며, 단일 조직/조직 내 여러 팀을 위한 기반 플랫폼
    - 따라서 테넌시 분리 및 라벨링, 권한 관리 등을 세세하게 설정할 필요가 없어 **Thanos의 단순한 모델이 더 적합**
    - 멀티 테넌시 기능은 복잡한 설정과 운영 부담을 유발하므로, **현재 요구사항 수준에서는 오히려 비효율**
