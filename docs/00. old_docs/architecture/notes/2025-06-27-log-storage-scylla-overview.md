# ScyllaDB 기반 로그 저장 전략 개요

> 🎯 중~대규모 비즈니스 로그 저장 및 분석을 위해 Elasticsearch 대신 ScyllaDB를 선택하게 된 배경과 구조적 판단을 설명한다.
> 
> 이 문서는 "정말 Elasticsearch가 아닌 ScyllaDB로 가는 것이 옳은 결정이었을까?"라는 질문에서 출발하여, ScyllaDB 선택의 타당성과 장기 운영 전략 측면에서의 우위를 재확인하기 위한 정리이다.

---

## 1. 의문

기존 EFK(Elasticsearch-Filebeat-Kibana) 구조에서 `Elasticsearch`를 제거하고,  
ScyllaDB를 로그 저장소로 사용하게 되면서 구조가 근본적으로 변화하였다.

Elasticsearch는 시각화, 자유로운 쿼리, DSL 기반 복잡 조건 처리 등 다양한 기능을 제공하지만,
- 과도한 리소스 소비 (JVM 기반)
- 샤딩, 노드 관리 복잡도
- 장기 저장의 부적합성 등을 이유로 로그 저장소로는 적절하지 않다고 판단되었다.
이에 따라, **단순 로그 저장 + 추적 기반 단건 조회**에 특화된 고성능 KV-Store인 `ScyllaDB` 도입을 검토하였고,  
그에 따른 구조적 전환이 적절했는지를 평가한다.

---

## 2. Elasticsearch 기반 로그 구조 개요

- 수집: Filebeat → Kafka → Elasticsearch
- 조회: Kibana + DSL
- 장점: 시각화/복잡 쿼리에 강함, 자유도 높은 조회 가능
- 한계:
    - JVM 기반 GC 문제, 인덱싱 지연
    - 샤드 분산에 따른 성능 불안정
    - 대량 로그 환경에서의 스토리지/리소스 부담
    - 클러스터 튜닝/운영 복잡도

---

## 3. ScyllaDB 기반 구조 도입 배경

- 수집: 구조화된 로그(JSON)를 Kafka로 전송 → Wrapping Service → ScyllaDB 저장
- 조회: Wrapping 또는 Monitoring 서비스에서 직접 조회, 혹은 KV 기반 조건 쿼리

### 선택 이유

1. **대량 쓰기 최적화**: Scylla는 Cassandra 기반의 log-append 패턴에 최적화되어 있음
2. **PK 기반 추적 단건 조회**에 적합: traceId, spanId, operationId 등
3. **Materialized View 지원**으로 다양한 조회 패턴 대응 가능
4. **낮은 레이턴시**: 자체 I/O 스케줄링으로 지연 최소화
5. **운영 간소화**: Elasticsearch 대비 백업/복원, 클러스터 유지비용 낮음

---

## 4. ScyllaDB 도입 후 구조적 이점

- **불필요한 분석 기능 제거**로 단순화된 저장 구조
- **Kibana 제거** → 시각화는 Grafana로 통합, 직접 조회는 Wrapping 또는 Scylla 조회로 처리
- **추적 기반 로그 수집/저장/조회 일원화**
- **비즈니스 로그 + 알림 조건 평가 시스템과의 통합 용이**

---

## 5. 결론

Elasticsearch는 로그뿐만 아니라 메트릭/트레이싱 등 다양한 기능을 수용할 수 있는 통합 분석 도구였지만,  
이번 프로젝트에서는 오히려 그 **범용성과 복잡성이 장애**였다.

ScyllaDB는 단순한 로그 저장, **추적 기반 조회**, 장기 보존 등 이번 시스템의 목표에 정확히 부합하였으며,  
장기적인 운영 비용, 확장성, 성능 측면에서도 더 유리하다는 결론에 도달하였다.

> 결과적으로 ScyllaDB는 단지 대체제가 아니라,  
> **이번 아키텍처에 가장 적합한 전략적 선택**이었다.
