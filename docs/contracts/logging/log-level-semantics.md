# 📄 로그 레벨 해석 기준 및 알림 연계 규약

> 로그 레벨은 단순한 출력 수준을 넘어서,  
> **서비스 상태, 오류 심각도, 알림 연계 정책에 영향을 주는 시스템적 신호 체계**입니다.  
> 본 문서는 로그 레벨의 해석 기준과 각 로그 유형별 최대 허용 레벨을 정의합니다.

---
## ✅ 목적

- 로그 해석의 **일관성 확보**
- **알림 연계 정책**과의 기준 통일
- 로그 수준에 따른 **모니터링/분석/추적 전략 구분**

---
## 🧭 로그 레벨 해석 기준


본 시스템은 운영 환경에서 아래 3가지 로그 레벨만을 실질적으로 사용합니다.  
이 기준은 알림 연계 정책 및 로그 해석의 일관성을 위해 강제됩니다.

| 레벨      | 설명                                                            | 알림 연계                               |
| ------- | ------------------------------------------------------------- | ----------------------------------- |
| `INFO`  | 정상 흐름 내 주요 이벤트 기록. 서비스 상태 변화 없이 단순 상태 또는 처리 흐름 정보             | ❌ 없음                                |
| `WARN`  | **경고 수준의 문제**. 비정상 상황이지만 기능 수행은 가능. 장애 전조 신호로 사용 가능           | 🔄 로그 정책에 따라 일부 연계 가능 (ex. act-log) |
| `ERROR` | **업무 로직 실패, 시스템 예외, 사용자 요청 처리 실패 등 치명도 높은 이슈**. 즉각 분석 및 추적 필요 | ✅ 대상                                |

다음 로그 레벨은 **운영 환경에서 사용되지 않으며**,  
개발 및 테스트 환경에서만 일시적으로 활성화할 수 있습니다.

| 로그 레벨   | 설명                                                         |
| ------- | ---------------------------------------------------------- |
| `DEBUG` | 상세한 상태, 변수 값, 조건문 흐름 등을 기록. dev 환경 디버깅 용도                  |
| `TRACE` | 메서드 단위의 입출력, 트랜잭션 흐름 등 매우 상세한 흐름 추적. Noise가 많아 운영에서는 비활성화됨 |

---
## 🔔 알림 연계 정책과의 연결

- `ERROR` 레벨은 **알림 시스템 전파 가능 대상**으로 간주됩니다.
- `WARN` 레벨은 **정책에 따라 알림 필터링 조건으로 사용될 수 있습니다.**
- `INFO` 레벨은 **알림 시스템과 연계되지 않습니다.**

> 📌 로그 레벨은 단순한 출력 제어 수단이 아니라,  
> 시스템이 상태를 외부로 전달하는 중요한 신호 체계입니다.  
> 개발자는 로그 레벨을 선택할 때 **의도와 해석 가능성**을 고려해야 합니다.

---
## 🧱 로그 유형별 최대 허용 레벨

| 로그 유형     | 최대 허용 레벨 | 이유                                           |
| --------- | -------- | -------------------------------------------- |
| `sys-log` | `WARN`   | 시스템 예외나 경고까지만 기록. 실제 장애는 infra 측에서 감지 또는 처리함 |
| `act-log` | `WARN`   | 상태 체크 결과 이상 시 사용. 단, 치명 오류는 별도 수단으로 감지함      |
| `biz-log` | `ERROR`  | 실제 업무 흐름 실패 기록. 알림 정책의 핵심 대상                 |

---
## ✍️ 개발자 가이드

- `INFO`: 흐름 또는 상태 전달용  
- `WARN`: 전조 신호 → 운영자가 상황을 파악해야 할 수도 있음  
- `ERROR`: **업무적 문제** → 반드시 사후 원인 분석 및 알림 연계 고려  

### 📌 StackTrace 출력 정책

- `ERROR` 레벨에서만 **stacktrace 포함 출력**을 허용합니다.    
    - 문제 발생의 **루트 원인 분석**을 위한 핵심 정보이기 때문입니다.
- `WARN`, `INFO` 등 다른 레벨에서는 **stacktrace 출력 금지**를 권장합니다.
    - 불필요한 로그량 증가를 방지하며, 경고 수준 이슈로 오해되는 것을 줄입니다.
- stacktrace는 `logback-spring.xml`에서 **레벨 조건에 따라 출력 여부를 제어**할 수 있습니다.  
    (예: 필터, custom provider 등을 이용)
- stacktrace는 개발 설정에서는 모든 로그가, 운영 환경에서는 축소 로그가 찍힙니다.
	- 참고: [logback-spring 설정 문서](guide/config/etc/logback-spring.md)

> ✅ 로그 레벨과 함께 **stacktrace 포함 여부**도  
> 서비스 이상 여부를 외부에 전달하는 **신호 체계의 일부**로 해석해야 합니다.

}
