# ScyllaDB 테이블 설계 및 조회 전략

## 1. Base Table 설계 목적

Base Table은 로그 저장의 **단일 진실의 원천(Source of Truth)** 역할을 하며, 모든 로그 데이터는 이 테이블에 먼저 저장됩니다.

- **모든 로그 필드**를 포함하여, 데이터의 완전성을 보장합니다.
- **최소한의 파티션 키(Partition Key)** 와 클러스터링 키를 조합하여, 특정 로그 묶음을 효율적으로 조회할 수 있도록 설계합니다.
- 일반적으로 `traceId`, `timestamp` 등의 컬럼이 키로 사용되며, 이는 시간순 로그 추적을 가능하게 합니다.
- **모든 조회는 최종적으로 Base Table을 기준으로 해야** 전체 로그 내용을 가져올 수 있습니다.
- 추후 스키마 변경 가능성에 대비하여, 유연한 컬럼 추가 및 TTL 정책과 병행되어 설계됩니다.

## 2. Materialized View (MV) 설계 목적

Materialized View는 특정 조회 목적(예: 분석, 통계, 추적 등)에 최적화된 **보조 인덱스 또는 전용 조회용 테이블** 역할을 합니다.

- 특정 분석 목적에 맞는 **파티션 키와 클러스터링 키 조합**으로 구성합니다.
- MV는 Base Table의 특정 서브셋을 복제한 구조이므로, **반드시 Base Table의 컬럼을 참조하여 생성**되어야 하며, 별도의 데이터를 보유하지 않습니다.
- MV의 컬럼은 다음 목적 중 하나에 해당해야 합니다:
    - Base Table에서 해당 데이터를 **직접 조회**하기 위한 최소 필드
    - 특정 조건에서 **카운트나 그룹 분석**에 필요한 필드
- MV는 특정 조건에 따라 자동으로 동기화되지만, eventual consistency 모델이므로 **정합성에 민감한 쿼리에는 주의가 필요**합니다.
- MV는 **조회 성능 최적화와 부하 분산**을 위해 사용되며, Base Table을 완전히 대체하지 않습니다.
## 3. 설계 철학 요약

- **Base Table**은 로그 전체를 저장하고, 추적 가능한 유일한 출처입니다.
- **Materialized View**는 쿼리 최적화를 위해 **읽기 패턴별로 추가 구성하는 보조 구조**입니다.
- MV는 Base Table의 신뢰성과 데이터를 전제로 하며, 모든 데이터 변경은 Base Table을 통해 이루어져야 합니다.
- **조회는 가능한 MV를 먼저 활용하되, 세부 로그가 필요할 경우 Base Table로 fallback**하는 구조가 권장됩니다.
