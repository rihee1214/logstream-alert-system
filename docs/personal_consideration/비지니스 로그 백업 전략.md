# 전반적인 백업 고민

## 백업 목적

많은 종류의 로그들이 존재하지만, 특히 비지니스 로그는 핵심 도메인들에 대한 로그이기 때문에 추후에도 그것을 보고 분석할 필요가 존재한다. 또한 고객과의 계약 상으로 중요한 요소가 됨으로 백업은 필수적이다.

## 백업 시간에 대한 고민

1. 실시간 : kafka에서 백업 서비스로 이동
2. 배치 : scyllaDB 한달에 한번식 백업(혹은 일주일에 한번)

> 가장 간단한 구현은 배치를 이용하여 백업.
> 실시간 저장소는 어렵기도하지만, datawarehouse처리시에도 OLTP 처리에 유용하지 않기 때문에 굉장히 애매함.
> **결국 배치를 이용한 저장이 제일 적절해보임. 관리 포인트도 적고, 정책에 대한 고민도 줄어들게됨**
> 추가적으로 history와 realtime 분석에 대한 전략이 필요해보임

## 백업 전략에 대한 고민

1. 별도의 DB에 원본 그대로 마이그레이션 하여 저장
2. File을 만들어서 아카이빙 및 압축 저장

> 해상도를 낮출 수는 없음. 해상도를 낮출 수 있는 요소가 전혀 없고, 삭제되는 로그 자체가 중요 데이터일 가능성이 높음
> **다만 비지니스 로그가 아닌 로그들은 해상도를 낮추는 것에 대한 고민이 필요할 수 있음**
> System log의 경우 warn이상의 로그는 그대로 두고. info 레벨만 해상도를 낮추는 전략을 사용할 수 있음.
> actuator로 자기의 생존을 알리는 로그의 경우 해상도 낮추는 것은 크게 문제 없을것으로 보임


## 백업 데이터 분석에 대한 고민

1. 필요한 시기의 데이터를 import한 후 적절한 쿼리로 분석 및 확인
2. 모든 데이터를 저장소에 두고 데이터 웨어하우스, 데이터 레이크 솔루션을 이용하여 분석
3. 모든 데이터를 클라우드 저장소에 두고, 분석 솔루션 및, history 분석 프로그램을 구현

> 구현 난이도는 물론 import 방식이 제일 쉽지만, 제대로 된 분석 시스템을 두기 어려울 수 있음.
> 모든 데이터를 저장소에 두고 데이터 웨어하우스, 데이터 레이크 솔루션을 이용한다는 방법은 굉장히 유용하나 데이터 웨어하우스 유지비용과 관리 비용이 많이 들어갈 것으로 보임
> 세번째 방안이 가장 좋아보이나, 문제는 클라우드 저장소 여러개를 사용하기는 많이 번거로울거같고, 추후 데이터 이동에 대한 제약이 심해보임

## 백업 데이터 암호화에 대한 고민

1. DB 저장 
	- 기본적으로 접근 제어를 사용하기 때문에 열람이 어려움.
	- 간단한 수준의 OS 암호화로 충분함
2. 파일 기반 백업
	- **반드시 압축 + 암호화 필요**
3. object storage
	- 클라우드 기반의 경우 DDoS어택으로 인한 과도한 비용 청구 문제도 있어서 추가 접근제어 및, 암호화가 필요할 가능성이 높음.

> 비즈니스 로그는 예외 없이 **고객 식별 정보, 요청 파라미터, 실패 사유 등 민감한 정보**를 포함할 수 있음
> **로그는 민감 데이터가 포함된 개인정보 덩어리로 간주하고 보호해야함**

---
## 백업 데이터 복원에 대한 전략

> 데이터를 복원하거나, 사용할 수 있도록 해야 분석이 가능하기 때문에 어떻게 할지 정의해야함
> 다만 어떤 방식으로 데이터를 백업할지에 대한 고려가 되어있지 않기 때문에 복원에 대한 전략 또한 미리 지정할 수 없음.
