# 전반적인 백업 고민

## 백업 목적

많은 종류의 로그들이 존재하지만, 특히 비지니스 로그는 핵심 도메인들에 대한 로그이기 때문에 추후에도 그것을 보고 분석할 필요가 존재한다. 또한 고객과의 계약 상으로 중요한 요소가 됨으로 백업은 필수적이다.

## 백업 시간에 대한 고민

1. 실시간 : kafka에서 백업 서비스로 이동
2. 배치 : scyllaDB 한달에 한번식 백업(혹은 일주일에 한번)

> 가장 간단한 구현은 배치를 이용하여 백업.
> 실시간 저장소는 어렵기도하지만, datawarehouse처리시에도 OLTP 처리에 유용하지 않기 때문에 굉장히 애매함.
> **결국 배치를 이용한 저장이 제일 적절해보임. 관리 포인트도 적고, 정책에 대한 고민도 줄어들게됨**
> 추가적으로 history와 realtime 분석에 대한 전략이 필요해보임

## 백업 전략에 대한 고민

1. 별도의 DB에 원본 그대로 마이그레이션 하여 저장
2. File을 만들어서 아카이빙 및 압축 저장

> 해상도를 낮출 수는 없음. 해상도를 낮출 수 있는 요소가 전혀 없고, 삭제되는 로그 자체가 중요 데이터일 가능성이 높음
> **다만 비지니스 로그가 아닌 로그들은 해상도를 낮추는 것에 대한 고민이 필요할 수 있음**
> System log의 경우 warn이상의 로그는 그대로 두고. info 레벨만 해상도를 낮추는 전략을 사용할 수 있음.
> actuator로 자기의 생존을 알리는 로그의 경우 해상도 낮추는 것은 크게 문제 없을것으로 보임


## 백업 데이터 분석에 대한 고민

1. 필요한 시기의 데이터를 import한 후 적절한 쿼리로 분석 및 확인
2. 모든 데이터를 저장소에 두고 데이터 웨어하우스, 데이터 레이크 솔루션을 이용하여 분석
3. 모든 데이터를 클라우드 저장소에 두고, 분석 솔루션 및, history 분석 프로그램을 구현

> 구현 난이도는 물론 import 방식이 제일 쉽지만, 제대로 된 분석 시스템을 두기 어려울 수 있음.
> 모든 데이터를 저장소에 두고 데이터 웨어하우스, 데이터 레이크 솔루션을 이용한다는 방법은 굉장히 유용하나 데이터 웨어하우스 유지비용과 관리 비용이 많이 들어갈 것으로 보임
> 세번째 방안이 가장 좋아보이나, 문제는 클라우드 저장소 여러개를 사용하기는 많이 번거로울거같고, 추후 데이터 이동에 대한 제약이 심해보임

## 백업 데이터 암호화에 대한 고민

1. DB 저장 
	- 기본적으로 접근 제어를 사용하기 때문에 열람이 어려움.
	- 간단한 수준의 OS 암호화로 충분함
2. 파일 기반 백업
	- **반드시 압축 + 암호화 필요**
3. object storage
	- 클라우드 기반의 경우 DDoS어택으로 인한 과도한 비용 청구 문제도 있어서 추가 접근제어 및, 암호화가 필요할 가능성이 높음.

> 비즈니스 로그는 예외 없이 **고객 식별 정보, 요청 파라미터, 실패 사유 등 민감한 정보**를 포함할 수 있음
> **로그는 민감 데이터가 포함된 개인정보 덩어리로 간주하고 보호해야함**

## 백업 데이터 복원에 대한 전략

> 데이터를 복원하거나, 사용할 수 있도록 해야 분석이 가능하기 때문에 어떻게 할지 정의해야함
> 다만 어떤 방식으로 데이터를 백업할지에 대한 고려가 되어있지 않기 때문에 복원에 대한 전략 또한 미리 지정할 수 없음.

## 파일 암호화에 대한 분석

| 항목            | zip                                      | 7z (7-Zip)                           | 비고                        |
| ------------- | ---------------------------------------- | ------------------------------------ | ------------------------- |
| **압축 알고리즘**   | Deflate (기본)                             | LZMA, LZMA2, PPMd, BZip2 등           | 7z는 다양한 고효율 알고리즘 선택 가능    |
| **압축률**       | 평균 30~40% 압축, 낮은 CPU 사용                  | 평균 50~70% 압축, 높은 효율                  | 7z가 평균적으로 더 높은 압축률        |
| **압축 속도**     | 매우 빠름 (간단한 연산 구조)                        | 비교적 느림 (복잡한 압축 알고리즘 연산 포함)           | zip이 빠르며, 7z는 CPU 사용량이 높음 |
| **암호화 지원**    | AES-128 (zipx), ZipCrypto 등              | **AES-256 지원**, 전체 암호화 가능            | 7z가 보안성 면에서 훨씬 우수         |
| **파일 무결성 보호** | 기본 zip은 무결성 보호 미흡                        | **암호화 + 헤더 보호**로 무결성 및 메타데이터 보호 가능   | 7z는 파일 목록까지 보호 가능         |
| **호환성**       | Windows/macOS/Linux 대부분에서 기본 지원          | 모든 OS에서 사용 가능하나, **별도 프로그램 설치 필요**   | zip은 내장, 7z는 외부 CLI 도구 필요 |
| **운영 자동화**    | 쉬움 (`zip`, `unzip` 기본 명령어 사용 가능)         | 약간 번거로움 (`7z`, `7zr` 설치 후 CLI 사용 필요) | 스크립트 기반 자동화에서 zip이 편리     |
| **암호화 적용 방식** | 파일별 암호화 또는 선택적 암호화                       | **전체 압축 후 암호화**, 헤더 포함 가능            | 7z는 파일 목록조차 숨길 수 있음       |
| **보안 적합성**    | 낮음 ~ 중간 (기본 암호화 옵션은 약함)                  | **높음**, 보안 로그 저장 및 전송에 적합            | 민감 데이터 저장에는 7z 사용 권장      |
| **파일 크기 제한**  | zip 포맷은 4GB 제한 존재 (zip64로 확장 가능하나 제약 있음) | **TB 단위 이상 지원**, 대용량 데이터에 적합         | 장기 로그 보존 등에는 7z 유리        |
| **오픈 포맷 여부**  | 일부 구현이 사유적 형식(zipx 등)                    | **완전한 오픈 포맷**, 공개 스펙 제공              | 장기 보존, 상호운용성 측면에서 7z가 우수  |
정말 간단한 사용을 위해서라면 zip 방식이 제일 편할 것으로 보임.
그러나 보안성과 효율성을 위해서라면 무조건 7z를 사용해야함.
아키텍처적인 간편성을 위해 결정한 파일 저장방식이니, 세부 구현만큼은 보안성에 더 치중해야한다고 판단되기에 7z사용 예정

## 백업 데이터 저장 및 import 전략
1. sstable 로 데이터를 백업을 하면 빠른 백업 속도와 import 속도를 가지고 있어 효율성과 편이성 두개를 같이 챙길 수 있다.
2. 백업 전략은 다음과 같다.
	1. 매달 초가 되면 logging service가 kafka에 백업 관련 메시지를 날린다.
	2. kafka에 중복키 제거를 통해 단 하나의 메시지만 들어가게 한다.
	3. scyllaDB에는 TTL을 걸어야한다. 
	   백업은 한달에 한번 이루어지므로 테이블에는 한달치 내용 이상이 들어가 있어야 한다.
	   즉 32일, 33일 제한을 걸어야 한다.
	4. kafka 메시지에는 어떤 서비스의 로그를 백업할 것인지도 들어가 있어야 하고, 몇년 몇월의 데이터인지도 표시가 되어있어야 한다.
	   결국 {서비스명}-{YYYYMM} 과 같은 파일명으로 저장이 될 예정이다.
	5. 결국 메시지 발행을 logging service가 했지만, 소비도 logging service가 받아서 cql을 통해 백업을 진행하도록 만들고, 그것을 암호화 압축하여 저장소로 보내놓는 것 까지 역할을 잡아야 한다.
		```python
		from kafka import KafkaConsumer
		import subprocess
		import shutil
		import os
		import datetime
		
		TOPIC = 'backup-trigger'
		CLOUD_BACKUP_DIR = '/mnt/backup-s3'
		
		consumer = KafkaConsumer(
		    TOPIC,
		    bootstrap_servers='kafka:9092',
		    group_id='scylla-backup-agent',
		    auto_offset_reset='earliest'
		)
		
		for message in consumer:
		    print("Received backup trigger!")
		
		    # 1. Snapshot 생성
		    subprocess.run(['nodetool', 'snapshot', '-t', 'backup-202506'])
		
		    # 2. 스냅샷 압축
		    snapshot_dir = '/var/lib/scylla/data/<keyspace>/<table>/snapshots/backup-202506'
		    archive_file = f'/tmp/backup-{datetime.date.today()}.tar.gz'
		    subprocess.run(['tar', 'czf', archive_file, snapshot_dir])
		
		    # 3. 마운트 디렉토리로 이동
		    shutil.move(archive_file, CLOUD_BACKUP_DIR)
		    print("Backup completed.")
		```
	해당 코드를 scyllaDB의 사이드 카로 넣고 동작하게 한다. (가볍고, 도메인 특화적인 코드이기 때문)
