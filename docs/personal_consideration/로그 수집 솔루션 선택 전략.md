# 로그 수집 솔루션 선택 고민

## 1. 초기 선택: Logstash → Filebeat
- 처음에는 ELK 기반으로 `Logstash`를 고려했으나, 너무 무겁고 복잡하여 `Filebeat`로 전환함.
- Filebeat는 **경량 로그 수집기**로, 시스템 부하를 줄이고 **간단한 로컬 로그 수집**에는 적절하다고 판단함.

## 2. 새로운 요구사항 등장 및 기술 탐색

- 로그를 **Kafka로 전달**해야 하고, 향후 구조화된 로그를 **중앙 수집 및 분석**하는 구조를 염두에 두고 있었음.
- 로그 포맷 자체는 이미 **logback appender를 통해 JSON으로 구조화**되어 있으므로, 별도 파싱이나 변형 로직이 필요하지 않음.
- 단순한 로그 수집기 이상의 기능은 오히려 **불필요한 복잡성을 유발**하며, 오버엔지니어링이 될 가능성이 있음.
- 이에 따라, **Kafka 연동이 용이하면서도 가볍고 단순한 구조**를 갖춘 대체 솔루션을 적극적으로 탐색함.

### 🎯 탐색의 목적

- 지금까지 도입한 모든 로그 수집 관련 솔루션(Filebeat, Logstash 등)이 **현재 요구사항에 비해 과하거나 부적절한 측면**이 없는지 점검
- **보다 효율적인 대체제 존재 여부를 검증**하고, 장기적인 유지보수성과 운영 효율성을 함께 고려함
- 단순히 동작하는 것이 아닌, **비즈니스 아키텍처 전체 맥락에서 가장 합리적인 도구인지 판단**하고자 했음
- 해당 프로젝트는 **중~대규모 시스템의 기반 플랫폼 역할을 수행**해야 하며, **장기적인 안정성과 운영 비용**까지 감안한 솔루션 선택이 필수였음

## 3. 후보 비교
| 솔루션 | 장점 | 단점 |
|--------|------|------|
| **Filebeat** | Elastic과 강한 통합, 설정 쉬움 | Kafka 연동은 제한적, 구조화 로그에 적합하지 않음 |
| **Fluent Bit** | CNCF 후원, Kafka 연동 최적화, 매우 가볍고 빠름 | 복잡한 변형은 어려움 |
| **Logstash** | 강력한 파이프라인, 다양한 필터 | 무겁고, 리소스 사용량 큼 |
| **Vector** | 신기술, Rust 기반 성능, 유연성 높음 | 문서 부족, 커뮤니티 작음, 실사용 사례 적음 |

## 4. 최종 선택: Fluent Bit
### ✅ 선택 기준
1. **문서화/커뮤니티 활성화**: 실전 프로젝트에서는 문서 부족이 곧 생산성 저하로 이어지므로 Fluent Bit 우세
2. **파싱 불필요**: 구조화된 로그를 그대로 Kafka로 전달만 하면 되기 때문에 Fluent Bit의 가벼운 구조가 가장 적절
3. **리소스 효율**: 비즈니스 애플리케이션에 부담을 최소화해야 하므로 Filebeat보다도 경량인 Fluent Bit이 유리
4. **Kafka 연동**: Fluent Bit은 Kafka output을 공식 지원하고 있으며, 배치 설정과 백오프 정책도 유연하게 제공

---

## 5. 결론
- Fluent Bit은 **단순하면서도 Kafka 기반 중앙 로그 수집 구조에 적합**한 솔루션이며, 특히 **비즈니스 서비스에 최소한의 영향만 주면서도 목표를 완벽하게 충족**함.
- 해당 선택은 **아키텍처 구조와 실전 운영 전략**을 동시에 고려한 결정이었으며, **구체적인 설정과 성능 테스트는 추후 문서화 예정**.
- 기술적 선택은 단순 기능 구현이 아닌, **장기 운영 및 시스템 확장성까지 고려한 전략적 판단**이었음.
