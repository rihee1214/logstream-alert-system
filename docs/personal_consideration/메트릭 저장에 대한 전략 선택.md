# 메트릭 수집 및 알림 시스템 아키텍처 전략 비교

> 🎯 중~대규모 플랫폼에서 신뢰성 있는 메트릭 수집과 장기 알림 전략을 구성하기 위한 세 가지 아키텍처의 비교 분석 및 결론

## 1. **Prometheus + Alertmanager 조합 전략**

 >Alert 정의 및 관리가 Prometheus 내부에 있으며, 중앙 집중식 Alerting 구조.
 >AlertManager는 단일 구성체로 동작하며, 이중화 및 분산 처리에는 약함.
### ✅ 장점

- **가장 널리 사용되는 조합**으로 문서, 커뮤니티, 사례 풍부.
- Prometheus에서 직접 Rule 기반의 Alert 정의 → Alertmanager로 전송 → Slack, Email, Webhook 등으로 알림 전송 가능.
- **단순하고 빠른 구성**이 가능하며, 운영 복잡도가 낮음.

### ⚠️ 단점

- **Prometheus의 단일 인스턴스에 의존** → 장기 보존 불가, 장애 시 Alert 중단 가능.
- Alert Rule이 Prometheus에 강하게 결합됨 → 복잡한 Alert 환경에서는 관리 어려움.
- 수집한 메트릭의 장기 저장이나 이중화가 어렵고, 멀티 테넌트에 적합하지 않음.

---

## 2. **직접 만든 메트릭 수집 서비스 + Notification 서비스 조합 전략**

  >Alert 로직 자체도 개발자가 정의해야 하며, AlertManager와 무관함.
  >메트릭 저장에 대한 고려가 추가적으로 필요함.
### ✅ 장점

- **아키텍처 완전 자율 구성 가능**: Kafka 기반 파이프라인, 메트릭 필터링, custom alert policy, 등 마음대로 구현 가능.
- 일반적인 Prometheus + Alertmanager가 해결 못하는 **비즈니스 룰 기반 경고** 가능 (예: 영업일 기준 연속 실패 등).

### ⚠️ 단점

- **개발/운영 부담**이 큼: 시스템 전체를 직접 책임져야 함.
- **알림 신뢰도** 확보 어려움: retry 정책, deduplication, delivery 보장 등을 직접 구현해야 함.
- **재사용성/유지보수성 낮음**: 새로운 팀이나 서비스에 적용하기 어렵고, 기술 부채 증가 위험.

---

## 3. **Thanos / Mimir 등의 Prometheus 확장 솔루션 조합**

> 각 Prometheus 인스턴스가 AlertManager를 독립적으로 구성 → 분산 처리 구조
> Sharding 또는 Federation을 통해 AlertManager를 연합 구성 가능
> Alert rule을 중앙에서 버전 관리하려면 별도 config repository or CI/CD 연동 필요할 수 있음

### ✅ 장점

- **장기 보존, 수평 확장, 멀티 테넌시** 모두 가능.
- Prometheus 인스턴스 개별 구성 + Query Layer + Store Gateway → 단일 시스템처럼 동작.
- Alert도 각 Prometheus 인스턴스에서 처리되며, **AlertManager Sharding or Federation 구조**로 구성 가능.
- Mimir는 특히 Cortex 기반이므로 **멀티 테넌시 강화**, Kubernetes 환경에서 강력한 성능.   

### ⚠️ 단점

- **구성 복잡도 매우 높음**: S3/Object Storage 필요, compactor, ruler, querier 등 여러 컴포넌트 필요.
- Alert 전략이 분산되거나 중복될 수 있음 → 중앙집중 관리가 어려울 수 있음.
- 일반적인 SaaS 수준의 운영 환경 필요.


## 결론

### 📌 설계 의도 및 검토 목적

- 지금까지 도입한 프로젝트에 들어가는 모든 솔루션들이 **현재 요구사항에 비해 과하거나 부적절한 측면**이 없는지 점검
- **보다 효율적인 대체제 존재 여부를 검증**하고, 장기적인 유지보수성과 운영 효율성을 함께 고려함
- 단순히 동작하는 것이 아닌, **비즈니스 아키텍처 전체 맥락에서 가장 합리적인 도구인지 판단**하고자 했음
- 해당 프로젝트는 **중~대규모 시스템의 기반 플랫폼 역할을 수행**해야 하며, **장기적인 안정성과 운영 비용**까지 감안한 솔루션 선택이 필수였음
### ✅ 최종 선택: Thanos / Mimir 조합

### 🔍 선정 사유 요약

1. 중~대규모 시스템의 기반 플랫폼에서 동작하려면 수많은 비지니스 컨테이너들에 대한 메트릭을 수집해야함
	1. 각 비즈니스 컨테이너마다 개별 Alert Rule 적용이 필요할 수 있음
	2. 메트릭을 계속 저장하여, 나중에 필요 시 분석 할 수 있도록 해야 함
	3. HA 구성이 무조건 가능해야 지속적인 수집이 가능하며, 그러면서도 중복되지는 않도록 해야함
2. 효율적으로 작동해야함
	1. 하나의 인스턴스가 죽더라도 계속적으로 동작해야한다.
	2. 여러 컨테이너에서 발생되는 메트릭을 효율적으로 수집해야한다.
	3. 간단하게 메트릭을 수집할 수 있어야 한다.
	4. HA, 백업 전략까지 모두 고려했을 때 관리가 쉬워야 한다.
	5. 효율적이라는 것은 개발 관리의 문제도 있음. 직접 개발해야 한다면 그만큼 관리 비용이 들어가고, 팀 단위의 인력이 필요함.
	
>🚧 단순한 선호의 문제가 아니라, 시스템 규모와 운영 복원력을 고려했을 때 **사실상 선택지가 한정된 필연적인 결정**이었다.
>특히 운영 중인 다수의 컨테이너 기반 비즈니스 서비스에 대해 **모니터링의 신뢰성과 책임 분산**, 그리고 **팀/조직 규모 확장 시의 수용력**까지 고려한 전략이었다.
>💡 해당 선택은 단지 기술적 우위가 아니라, 중~대규모 플랫폼을 운영할 수 있는 조직적 자원을 전제로 한 전략적 결정이다.
