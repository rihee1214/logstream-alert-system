# 효율적인 비지니스 로그 저장 및 추적을 위한 DB 선택

## 🔍 전제 조건: 요구사항 요약

- 비즈니스 로그 저장용 DB
- **중-대규모 기업 플랫폼 수준**의 안정성, 확장성
- 추적 시스템이 접근 용이해야 함
- **일관성보다는 가용성** 우선 (최종적 일관성 허용)
- **백업 전략** 수립이 쉬워야 함
- **샤딩/레플리카** 설정 자동화 또는 단순화
- **App 레벨에서는 인지하지 못하는** 분산 처리 구조

---

## 1. **Apache Cassandra**

### ✅ 장점

- **분산성과 확장성 탁월**: 수평 확장 매우 쉬움
- CAP 중 **가용성(Availability) + 파티션 허용(Partition tolerance)** 지향
- Write 성능이 우수, 고가용성 보장
- **샤딩 자동화**, **노드 추가 시 거의 무중단**

### ⚠️ 단점

- **복잡한 쿼리 미지원**: 조인, 집계 등 불가
- **설정 난이도** 존재: 데이터 모델링 방식이 일반 RDB와 매우 다름
- 백업/복구는 수동으로 직접 설정 필요
- JVM 기반이라 **튜닝 이슈** 있을 수 있음

✅ **적합성 평가**: ★★★★☆  
→ 최종 일관성을 허용하고, 추적만 목적이라면 최적. 운영자 숙련도만 확보된다면 우수함.

---

## 2. **Amazon DynamoDB**

### ✅ 장점

- **완전관리형 NoSQL**, 자동 스케일링 및 복제
- 매우 높은 안정성과 글로벌 서비스 가능
- TTL, 백업, 보안, IAM 통합 등 편의성 탁월

### ⚠️ 단점

- 벤더 종속성 (AWS만 사용 가능)
- 비용 예측 어려움 (스파이크 시 요금 폭등)
- 복잡한 조건 쿼리 제한
- **on-premise 사용 불가**

✅ **적합성 평가**: ★★★☆☆  
→ 빠른 구축과 유지에 유리하지만, **벤더 종속과 운영비** 부담이 커서 솔루션 제품화에 부적합함.

---

## 3. **ScyllaDB**

### ✅ 장점

- **Cassandra와 호환되면서도** C++로 개발되어 성능 향상
- **노드당 처리량 매우 높음** (Cassandra 대비 3~10배 성능)
- **Low-latency, High-throughput**, NVMe 최적화
- **튜닝 요소 감소**, 자동화된 관리 기능 존재

### ⚠️ 단점

- 운영사 중심 커뮤니티 (ScyllaDB Inc.)
- Cassandra보다 **커뮤니티 작음**
- 일부 에코시스템 도구 호환성 주의

✅ **적합성 평가**: ★★★★★  
→ **Cassandra의 단점을 해소한 대안**. 당신이 직접 운영할 수 있다면 최고의 선택지.

---

## 4. **ClickHouse**

### ✅ 장점
- OLAP용 컬럼 지향 DB로 **고속 분석 쿼리** 가능
- **초고속 집계 성능**과 다차원 분석에 적합
- **수평 확장 및 클러스터링** 기능 존재

### ⚠️ 단점

- 실시간 write 처리에는 부적합
- 트랜잭션 기능 제한적
- **로그 수집 저장소보다는 분석 전용**에 적합

✅ **적합성 평가**: ★★☆☆☆  
→ **추적 및 실시간 로그 저장 용도에는 부적합**. 별도의 분석 DB로는 우수.

---

## 5. **Elasticsearch**

### ✅ 장점

- 강력한 **검색 기능**과 Kibana 시각화
- **실시간 색인 처리** 성능 우수
- 많은 SI 기업, 시스템에서 사용 경험 있음

### ⚠️ 단점

- 대량 데이터 저장에는 **성능/안정성 이슈** 존재
- **복잡한 클러스터 구성, GC이슈**, JVM 기반 한계
- 로그/메트릭/트레이싱을 모두 맡기기엔 **모놀리식화** 위험

✅ **적합성 평가**: ★★☆☆☆  
→ 중-대규모 시스템에서 장기 저장/안정성 측면에선 **부적합**. 이제는 점차 다른 솔루션으로 분리하는 추세.


## 각 DB의 CAP레벨

### 🔍 1. **Cassandra**

- **지향점**: **AP**
- **설계 철학**:
    - Partition Tolerance와 Availability를 우선
    - Eventual Consistency + Tunable Consistency(정족수)
- **주요 특징**:
    - 쓰기 성능 우선 (로그성 데이터에 강함)
    - 다중 데이터센터 지원
- **사용 시나리오**:
    - 대규모 로그 저장, IoT 데이터 수집, 시간 기반 이벤트 기록 등

---

### 🔍 2. **ScyllaDB**

- **지향점**: **AP** (Cassandra와 동일하되, **Latency & Performance 강화**)
- **설계 철학**:
    - Cassandra의 모든 특성 유지 + 성능 최적화
    - C++ 기반 shard-per-core 구조로 **tail latency 제거**
- **주요 특징**:
    - GC 없는 설계 → JVM 기반보다 훨씬 낮은 latency
    - Cassandra 드라이버 및 툴 100% 호환
- **사용 시나리오**:
    - Cassandra와 동일 + 고성능 요구되는 대용량 분산 로그 플랫폼

---

### 🔍 3. **DynamoDB (AWS)**

- **지향점**: **AP**    
    - 사실상 **PA를 극대화**한 구조 (Consistent Read는 선택적)
- **설계 철학**:
    - Availability와 Partition Tolerance 우선
    - AWS 내에서 탄력적인 스케일링 제공
- **주요 특징**:
    - 완전 관리형 (Managed)
    - Throughput 기반 요금 → 예측 가능한 비용 아님
- **사용 시나리오**:
    - 서버리스 아키텍처, AWS 내부 마이크로서비스, 빠른 개발 주기

---

### 🔍 4. **MongoDB**

- **지향점**: 기본적으로 **CP**    
- **설계 철학**:
    - Consistency 우선 + Replica Set 기반 가용성 확보
    - Network Partition 상황에서는 일부 쓰기 불가능할 수 있음
- **주요 특징**:
    - document 기반 쿼리 편의성
    - write concern, read preference로 세밀한 제어 가능
- **사용 시나리오**:
    - 비교적 강한 정합성이 필요한 CMS, 내부 비즈니스 도구 등

---

### 🔍 5. **ElasticSearch**

- **지향점**: **CA** (Strict하게 말하면 **선택적 CP**에 가까움)    
- **설계 철학**:
    - 대부분의 경우 Consistency와 Availability 우선
    - 하지만 Split-Brain 상황에서 Partition이 생기면 동기화 실패 가능
- **주요 특징**:
    - 실시간 검색, 인덱싱 우선
    - 분산 환경에서는 cluster 관리/consensus가 복잡함
- **사용 시나리오**:
    - 로그 분석, 텍스트 기반 검색, APM, 모니터링 대시보드 등

---

지금까지 상황을 보았을때, ScyllaDB가 제일 적절한 판단이지만, 문제는 그렇게 될 경우 아키텍처적 계약 문제가 걸린다.
MDC세팅을 자유롭게 해서 어떤 사용자든 자기가 추가하고 싶은 요소들을 추가할 수 있도록 했는데, ScyllaDB, Cassandra를 사용하게 된다면 해당 요소들은 Column Oriented DB라 이미 스키마가 정해진 상태여야 한다.
관계형 데이터 베이스보다 스키마를 추가하기 쉬울지언정, 해당 내용은 정말로 추가해야할 요소인가를 고려해야하고, 굉장히 무거운 결정 과정을 거쳐야하기에 로그 스키마에 대한 내용은 고정이 되게 된다.
심지어 DB에서 모든 로그를 불러올때 컬럼 지향 아키텍처는 단점이 되어 버린다. 
관계 지향 아키텍처와 다르게 각 컬럼 단위로 저장되기 때문에 전체를 가져오려면 모든 컬럼을 다 뒤져서 가져오는 상황이 벌어지게 된다.

| 항목             | Elasticsearch         | ScyllaDB        |
| -------------- | --------------------- | --------------- |
| **자유로운 필드/쿼리** | ✅ 뛰어남                 | ❌ 제약 큼          |
| **대량 데이터 저장**  | ❌ 비용↑, 튜닝 필요          | ✅ 훨씬 유리         |
| **전체 로그 탐색**   | ✅ 기본 기능               | ❌ 불가능 또는 위험     |
| **운영 단순성**     | ❌ 클러스터, 샤드, 메모리 복잡    | ✅ 단순하지만 설계 제약 큼 |
| **MDC 확장성**    | ✅ 자유롭게 필드 추가          | ❌ 사실상 고정 스키마    |
| **성능**         | 🔁 인덱스 기반 (조건에 따라 다름) | ✅ 키 기반 고속 읽기/쓰기 |
