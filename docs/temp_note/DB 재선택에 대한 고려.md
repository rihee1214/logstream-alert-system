# ScyllaDB/Cassandra 도입에 대한 회고와 PostgreSQL로의 전환 고려

## ScyllaDB 및 Cassandra 사용 시 문제점

### 1. **테스트 환경 구성의 어려움**

- Seastar 기반 아키텍처로 인해 **Docker 기반 개발 환경에서도 제약**이 많음.
- Windows 환경에서는 **정상적인 테스트 실행조차 어려움**.
- 클러스터 환경을 흉내 내기도 어렵고, **단일 노드 테스트만으로는 실운영 시나리오를 재현하기 힘듦**.

### 2. **운영 및 유지보수 복잡도**

- **기초 설계 및 데이터 모델링 학습이 필수**이며, 단순 CRUD 수준으로 접근하기 힘듦.
- 클라우드 환경에서도 설치/운영이 단순하지 않으며, **스토리지 설정 및 replication 관리 등 인프라적 지식이 요구됨**.
- **Schema 변경이나 확장 시 트러블슈팅 난이도도 높음.**

### 3. **Select/조회의 비유연성**

- 복잡한 조회가 어려워 **사전에 MV(Materialized View)를 설계**해두어야 함.
- MV 관리 부담이 큼:
    - 너무 많은 MV를 생성하면 **쓰기 성능 저하 및 운영 관리 포인트 증가**.
    - MV 기반 조회 후, 다시 메인 테이블을 조회해야 하는 경우도 있어 **쿼리 2회 발생**.
    - MV에는 **필요 이상으로 많은 필드가 들어가는 경우**가 많아, Application 단에서 **불필요한 데이터 필터링 필요 → 성능 저하**.

### 4. **백업 및 마이그레이션 도구 부재**

- **공식적인 backup/migration 툴이 부재**하여, 직접 구현 필요.
    - 결과적으로 **관리 포인트가 증가**하며, 버전 업그레이드나 클러스터 교체 시 **예상치 못한 문제가 발생**할 가능성이 높음.
    - 백업 이후 스키마 재적용 → MV 재생성 → application 수정 → 운영 리스크 증가.

### 5. (사용하지 않으나 현실적인 한계) **ACID 트랜잭션 미지원**

- 단일 파티션 내 경량 트랜잭션은 가능하지만, **다중 파티션 간 원자적 처리 불가능**.
- Kafka 등의 비동기 시스템과 연동 시 **Outbox 패턴도 제한적으로만 적용 가능**.
- 결국 **이중 처리(dual write)** 문제에 대한 해결책을 별도로 마련해야 하며, **신뢰성을 보장하기 어려움**.

## PostgreSQL 선택 기준

### 1. **PostgreSQL의 선택 이유 (선정 우위 항목)**

| 항목             | PostgreSQL                                                | ScyllaDB/Cassandra      |
| -------------- | --------------------------------------------------------- | ----------------------- |
| ✅ **쿼리 유연성**   | SQL, JOIN, Subquery, Aggregation, View, JSON 연산 등 강력한 표현력 | 단순 PK/RK 기반 조회 중심       |
| ✅ **스키마 유연성**  | `ALTER TABLE`, JSONB로 유연한 확장 가능                           | 스키마 변경 시 설계 재검토 필요      |
| ✅ **사용 용이성**   | SQL 표준 기반, ORM 및 다양한 툴 지원 (DBeaver, pgAdmin 등)            | NoSQL 특화 DSL 및 설정 필요    |
| ✅ **운영 및 백업**  | `pg_dump`, PITR(지점 복구), WAL 기반 백업/복구 구조 완비                | SST 기반 스냅샷 또는 별도 툴 필요   |
| ✅ **분석 적합성**   | CTE, Window Function, Materialized View 등 분석에 최적화         | 통계 및 분석 기능 미약           |
| ✅ **통합 및 생태계** | Kafka, Logstash, Grafana 등과의 통합 예제/도구 풍부                  | 제한적 도구 통합               |
| ✅ **확장성**      | 파티셔닝, 샤딩(Citus 등), 로우/콜드 스토리지 옵션까지 존재                     | 수평 확장 강점 있으나 관리 복잡      |
| ✅ **성숙도**      | 25년 이상 성숙된 RDBMS, 대형 기업 및 정부 시스템에서도 사용                    | 상대적으로 비교적 최근 도입됨        |
| ✅ **개발자 친화성**  | ORM, JDBC, REST API 등 다양한 접근 방식 지원                        | 코드 제약 많음 (Mapping 등 필요) |


---

### 2. **적용 시나리오 및 기대 효과**

| 적용 시나리오  | PostgreSQL 기반 기대 효과                                        |
| -------- | ---------------------------------------------------------- |
| 로그 저장    | 구조화된 테이블 설계 + JSONB로 반정형 로그도 수용 가능                         |
| 복잡한 분석   | Aggregation + Group By + Index + Materialized View로 고성능 분석 |
| 스키마 확장   | 버전 관리 + 점진적 변경 용이 (`ADD COLUMN`, `ALTER TYPE` 등)           |
| 백업/복원    | `pg_basebackup`, `WAL` 재생, 특정 시점 복구 등 다양한 옵션 확보            |
| 로그 레벨 관리 | Partial Index, Partitioning 등을 통해 Info/Debug 등 필터링 처리 용이   |
| 개발자 연동   | ORM(JPA, MyBatis, SQLAlchemy 등)과 즉시 연동 가능                  |

---

### 3. **기술적 고려사항 및 대응 방향**

| 고려 항목            | PostgreSQL에서의 대응 방식                                             |
| ---------------- | --------------------------------------------------------------- |
| **고속 Insert 성능** | Batch Insert, Unlogged Table, Copy 기능, Partition + Parallel WAL |
| **대용량 저장 공간**    | 테이블 파티셔닝 + 테이블스페이스 분산 저장                                        |
| **로그 적재량 증가**    | 압축 저장 (`TOAST` + `lz4/zstd`), 아카이빙 전략 가능                        |
| **수평 확장**        | Citus, Greenplum, TimescaleDB 등으로 샤딩 또는 병렬화 가능                  |


---

### 4. 결론 및 추천

> **PostgreSQL은 단순 저장뿐만 아니라, 분석·운영·확장성 측면에서도 성숙한 기능을 제공하며, 로그 저장 및 백업 시스템에 최적의 선택이다.**
> 특히, **변화하는 스키마**와 **복잡한 쿼리**, **운영 편의성**이 중요한 상황에서는 NoSQL보다 월등한 장점을 가진다.

---

## ✅ 결론: 실질적 가치의 재평가

- ScyllaDB/Cassandra는 분산 처리 및 초고속 쓰기 성능에 강점이 있으나, **운영의 복잡도와 유지 비용이 너무 크다**.
- PostgreSQL은 일부 성능상 한계가 있을 수 있지만, **테스트 환경, 운영 안정성, 유지보수 측면에서 훨씬 더 높은 가치를 제공**한다.
- 궁극적으로, **“더 좋아 보이는 것”이 “더 좋은 것”은 아니었다**는 사실을 다시금 확인하게 되었고, 실용적인 선택의 중요성을 체감했다.
