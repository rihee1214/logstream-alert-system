
# 테스트 코드의 중요성

1. **구조 변경 및 리팩토링 후 안정성 검증의 핵심 수단이 되었다.**
    - 코드의 구조를 변경하거나 리팩토링을 수행한 후에도, 테스트 코드를 통해 기존 로직이 그대로 유지되고 있는지를 빠르게 검증할 수 있었다.
    - 이는 **예상치 못한 부작용**이나 **비의도적 변경**을 방지하는 데 큰 역할을 했다.
        
2. **작은 수정부터 큰 구조 변경까지, 일관된 안전망 역할을 수행했다.**
    - Enum의 항목 추가, 리소스 위치 변경, 모듈 분리 등 다양한 변화가 있었지만, 테스트 코드를 통해 그 변화가 **기존 동작에 어떤 영향을 미치는지** 확인할 수 있었다.
    - 결과적으로, 기능 확장과 구조 개선이 동시에 가능한 개발 기반을 마련할 수 있었다.
    
3. **설정 오류를 조기에 감지하고, 빠르게 수정할 수 있었다.**
    - 예를 들어, `logback-spring.xml` 설정 변경 시 `spring.profile`이 제대로 적용되지 않아 로깅에 문제가 발생했었고, 테스트 코드를 통해 이를 즉시 파악할 수 있었다.
    - 설정 변경은 자칫 서비스 전반에 영향을 줄 수 있기 때문에, 테스트를 통해 **사전에 문제 지점을 명확히 식별할 수 있다는 점**이 큰 장점이었다.

# ScyllaDB 선택을 중심으로

1. **설계와 솔루션 선택은 생각보다 훨씬 어렵다.**  
   ScyllaDB를 선택한 과정을 통해 이 사실을 절감했다.
   단순히 성능만 보고 특정 솔루션을 선택하면 안된다는 교훈을 얻었다.
	
2. **ScyllaDB를 선택한 이유는 다음과 같다.**
	- 클라우드 환경에 적합한 복제/샤딩 구조를 갖추고 있어야 한다.
	- 인스턴스가 빠르게 생성되어야 한다.
	- 높은 INSERT 처리 성능이 필요하다.
	- 트랜잭션 추적이 가능하고, 조회 성능도 일정 수준 이상이어야 한다.
	
3. **하지만 개발을 진행하면서 예상하지 못했던 문제들이 드러났다.**
	1. **운영과 설정의 난이도**
	    - 내부 구조를 이해하지 않으면 초기 설정 자체가 어렵다.
	    - 백업 전략이나 스키마 추가 전략이 명확한 가이드 없이 직접 설계되어야 하며,  
	        특히 스키마는 클라이언트 라이브러리에서 캐시되기 때문에  
	        변경이 application 동작에 영향을 미치기도 한다.
	    - ScyllaDB는 seastar 프레임워크 기반으로 동작하기 때문에  
	        성능 최적화를 위해 호스트의 IO 구조나 CPU 코어 구조를 이해해야 한다.
	    - MV(Materialized View)를 추가하여 쿼리를 다르게 구성하는 경우, 
	      application 레벨에서 조합하는 것은 비교적 괜찮지만,  
	      MV 자체를 새로 만들어야 하는 경우 굉장히 번거롭고 위험하다.
	2. **테스트 환경의 제약**    
		- Seastar는 리눅스 전용 스케줄러 기반으로 동작하며,  
		  윈도우 환경에서는 도커 이미지로도 제대로 실행되지 않는다.
		- 개인 개발자 입장에서 환경 구성과 기초적인 테스트조차 어려웠다.
	3. **트랜잭션(ACID) 미지원**
		- INSERT 쿼리는 실행 즉시 커밋되어, 다중 연산 중 일부 실패 시 롤백이 불가능하다.
		- Outbox 패턴을 시도하려 해도, 서로 다른 파티셔닝 키를 가진 경우에는  
			하나의 쿼리로 묶을 수 없고, 결국 atomic하지 않게 된다.
	
4. **가장 근본적인 문제는, 솔루션 선택의 기준이 명확하지 않았다는 점이다.**
    - 단순히 내가 원하는 요구사항을 충족하는지에만 집중했고,  
        반대로 **그 선택이 야기할 수 있는 단점은 충분히 분석하지 못했다.**    
    - 예를 들어 Prometheus의 경우 자체 TSDB를 보유하고 있음에도  
        장기 저장 전략(S3 등)에 대한 고려가 미흡했다.  
        결과적으로 이후 Thanos 등의 재구성이 필요했고,  
        초기 판단에 대한 재평가가 뒤늦게 이루어졌다.
## 결론 
1. **겉보기엔 더 좋아 보이는 기술이 실제로 더 나은 선택은 아니라는 점을 깨달았다.**
    - 특히, 스펙상 뛰어난 성능이나 최신 기술이라는 이유만으로 선택했을 때, 정작 개발과 운영 과정에서 막대한 시간과 에너지를 소모할 수 있다는 교훈을 얻었다
	
2. **운용성과 사용 편의성은 실질적인 성능 우위보다 훨씬 더 중요한 가치임을 확인했다.**
    - 성능이 아무리 뛰어나도, 설정이 복잡하거나 플랫폼 제약이 심한 기술은 결국 **전체 비용(TCO: Total Cost of Ownership)**을 증가시킨다.
    - 이번 ScyllaDB 사례에서 보듯이,
        - 윈도우 기반 테스트 환경에서는 제약이 많았고,
        - 복잡한 설정과 운영 지식(Seastar, 파티셔닝 키, MV 설계 등)이 요구되었으며,
        - 네트워크 레벨의 복제 구조나 분석 쿼리 확장에 한계가 있었다.
    - 이러한 점은 단순한 “러닝커브”를 넘어서, 실제 유지보수 및 확장 시 **비용 부담 요소**로 작용한다.

# 결정 문서에 대한 인식과 운영 전략

## 1. 결정 문서는 **전체 아키텍처에 영향**을 주는 중요한 사항만 다룬다

- 결정 문서는 시스템 전체에 영향을 미치거나, 복수의 컴포넌트/모듈 간 **상호작용 및 경계 조건을 변경**하는 경우에 작성해야 한다.
- **설계 변경**이나 **아키텍처 방향성 결정**, 또는 **운영 정책 변경** 등 _범위가 크고 장기적으로 영향을 줄 수 있는 사안이 그 대상이다._

### ❌ 과도한 결정 문서 작성의 부작용

- 너무 세세한 구현 수준의 사항까지 문서화하면, 관리 부담이 커지고 문서 간 중복이 발생한다.
- 예: `MDC 핸들러`, `traceId / spanId 정책`, `log structure 내부 필드 결정` 등의 내용은 해당 서비스 내부 구현에 가깝고, **단일 서비스의 개발자 간 공유**로도 충분하다.

## 2. 결정 문서와 정책 문서의 경계는 명확히 나눠야 한다

- `traceId`, `log schema`, `spanId` 등은 분명히 **공통 정책에 해당**하며, 모든 서비스가 동일한 규칙을 따라야 한다.
- 이런 내용은 **정책 문서**에 통합 관리하고, **결정 문서에는 해당 정책이 왜, 언제, 어떤 이유로 도입되었는지만 요약**하는 것이 적절하다.
- 결정 문서는 “**왜 그렇게 하기로 했는가**”를 기록하는 문서이지, "**어떻게 할 것인가**"를 자세히 설명하는 가이드는 아니다.

## 3. 결정 문서 작성 기준

| 작성 여부 판단 기준        | 예시                       | 문서화 필요성          |
| ------------------ | ------------------------ | ---------------- |
| 아키텍처 변경 여부         | ScyllaDB → PostgreSQL 변경 | ✅ 필요             |
| 주요 컴포넌트 간 연동 방식 변경 | Kafka → gRPC로 알림 전달 변경   | ✅ 필요             |
| 특정 컴포넌트 내부 정책 조정   | MDC 전파 방식 개선             | ❌ 생략 가능 (정책 문서로) |
| 로그 필드명/형식 조정       | log_level → severity     | ❌ 생략 가능 (정책 문서로) |
| 운영에 직접적 영향         | 백업 주기 조정, 장애 대응 구조 변경    | ✅ 필요             |

## 4. 결정 문서의 목적과 역할

- 결정 문서는 *“나중에 왜 이렇게 되었는지를 설명할 수 있어야 한다”*는 단 하나의 목적을 가진다.
- 즉, **"설계가 잘 되어 있다면 굳이 들여다볼 필요 없는 문서"**가 되어야 하며,
- 변경 이력을 남기되, 그 자체가 실행 지침서는 아님을 인지해야 한다.

## ## 5. 개인적으로 느낀 개선 포인트 요약

- **결정 문서의 작성 기준을 명확히 정의하자.**
    - 사소한 변경이나 단기 정책이 아닌, 아키텍처 전반에 영향을 미치는 핵심 결정만 포함하자.
- **정책 문서와 결정 문서를 분리하여 관리하자.**
    - 정책은 반복적 실행을 위한 기준이고, 결정은 변화의 판단 근거이다. 성격이 다르므로 분리해야 한다.
- **결정 문서는 '정보 저장'이 아닌 '판단의 근거'를 남기는 도구라는 점을 인식하자.**
    - 기록은 로그로 충분하다. 왜 그 결정을 내렸는지를 설명하는 데 초점을 맞추자.
- **문서의 공유 목적과 범위를 명확히 설정하자.**
    - 조직에 공유되는 문서는 ‘누가, 왜 읽는가’에 따라 구조와 형식을 구분하자.
- **결정 문서의 템플릿은 상태(보류, 완료, 기각 등)에 따라 변경되지 않도록 유지하자.**
    - 문서 구조가 일관되어야 이후 회고나 비교가 쉬우며, 상태는 메타 정보로 구분해 관리하는 것이 바람직하다.

# 설계에 대한 회고

프로젝트 초반과 책을 통해 설계를 공부할 때는 막연한 상태였지만, 실제 진행을 하면서 몇 가지 중요한 점을 뼈저리게 느꼈다.  
처음에는 내가 생각보다 잘못된 전제를 가지고 있었고, 그로 인해 불필요한 시간 낭비와 설계 혼란이 발생했다.

---

## 1. MVP에 대한 오해
**잘못된 이해**  
- MVP를 “핵심 모듈만 빠르게 만들고 넘어간다”로 생각했다.  
- 그래서 전체 설계를 다 한 뒤, 각 컴포넌트를 가볍게 만들어만 놓고 다음 단계로 넘어가는 방식으로 접근했다.

**실제 깨달음**  
- MVP의 본질은 **전체를 얇게 만들기**가 아니라, **도메인 기준으로 나눈 일부 기능을 우선 완성**하는 것이다.  
- 내 프로젝트라면 다음과 같이 명확히 쪼개야 했다.
  1. 로그 수집기  
  2. 모니터링 서비스  
  3. 알림 서비스  
- 이 중 하나를 먼저 완성하고, 검증 후 확장했어야 한다.

---

## 2. 잘못된 “간단 구현” 접근법
**문제 상황**  
- 모든 요소를 “간단하게 만들어두자”는 생각이 오히려 전체 설계를 먼저 하게 만들었다.  
- 설계가 구체화될수록 수정사항이 늘어나고, 그에 따라 문서와 구조를 계속 갈아엎게 됐다.
- 특히 다음 두 사례가 대표적이다:
  - **Elasticsearch**:  
    - 내 프로젝트의 **구현 수준과 요구사항을 구체적으로 정의하지 않은 상태**에서, “많이 쓰니까”라는 이유만으로 선택했다.  
    - 실제 필요성과 맞는지, 운영 부담은 어떤지에 대한 검토 없이 단순 채택한 것이 문제였다.
  - **ScyllaDB**:  
    - 사용 수준과 성격은 고려했지만, **정작 직접 테스트 가능 여부**를 확인하지 않았다.  
    - 로컬 환경에서 프로토타입조차 만들지 못한 상태에서 설계에 반영해버린 것이 잘못이었다.

**원인**  
- 설계가 자주 바뀔 수 있다는 점은 알았지만, **작업 단위를 도메인 기준으로 작게 만드는 개념**이 없었다.  
- “컴포넌트 크기를 줄인다”에만 집중했고, **더 상위 수준의 기능 단위(도메인 단위)**로 쪼개는 것을 놓쳤다.

**깨달음**  
- 빠르게 만들고, 빠르게 검토하고, 빠르게 버리는 것이 MVP 정신이며, 이를 위해서는 **작업 범위를 도메인 단위로 작게 설정**해야 한다.  
- 기술 선택은 반드시 **구체적 요구사항 + 실제 테스트 가능성**을 검증한 뒤 해야 한다.

---

## 3. 도메인 인식 부재
**초기 오해**  
- 이 프로젝트는 플랫폼 성격이 강하니, 별도의 도메인 구분이 필요 없다고 생각했다.

**실제 문제**  
- 도메인을 나누지 않으니:
  - 로그 수집과 알림이라는 큰 흐름에서 세부 기능 구분이 안 됨
  - 문서화에만 시간이 흘렀고, 구조를 유지하지 못함
  - 판단 기준이 흐려져 잘못된 결정이 누적

**깨달음**  
- 도메인은 돈이 되는 비즈니스 기능에만 해당하는 것이 아니라, **플랫폼에서도 문제 해결 단위로 존재**한다.  
- 이를 인식하고 초기에 잘라놓았어야 했다.

---

## 4. 앞으로의 개선 방향 (액션 아이템)
1. **기능 단위로 MVP 범위 설정**  
   - 전체 설계를 다 한 뒤 얇게 구현하는 게 아니라, 도메인별 완결 기능 하나씩 만들기
2. **작업 단위 명확화**  
   - 컴포넌트 크기 축소뿐 아니라, 더 상위 수준의 기능 단위에서도 범위 축소
3. **도메인 맵 작성**  
   - 플랫폼이라도 도메인을 정의하고, 그 경계별로 책임을 구분
4. **설계-구현-검증 주기 단축**  
   - 최대 1~2주 단위로 피드백 가능한 산출물을 만들 것
5. **문서화 비중 조정**  
   - 설계 초기에는 필요한 범위까지만 문서화, 검증 이후 확장

# Observability에 관하여

## 1. Engineering Observability를 읽으며
책을 약 3/4 정도 읽은 시점이라 완전한 이해라고 할 수는 없지만, 그럼에도 불구하고 많은 인사이트를 얻었고 이를 바탕으로 회고를 남긴다.

---

## 2. 프로젝트에서 생각이 진행된 과정
1. 처음에는 단순한 **로그 수집**을 목표로 했다. 그런데 모으고 보여주는 행위 자체가 결국 **모니터링**을 향한다는 사실을 뒤늦게 자각했다.
2. 결과적으로 이름은 *MSA-LOG*였지만 실제로는 **전체 모니터링 서비스**를 지향하게 됐다.
3. “모든 로그를 추적으로 연결 가능하게 만들자”라는 목표를 세웠다.
4. 당시 Observability 개념을 충분히 이해하지 못해, **로그와 Observability가 섞인 설계**(traceId, spanId, serviceId를 전 로그에 강제)로 흘렀다.
5. 시작도 전에 너무 많은 설계를 한꺼번에 끌어안았고, 전제가 잘못되었다는 걸 뒤늦게 깨달았다.

---

## 3. 한계점
1. **추적 가능 요소를 모든 로그에 강제**하려다 보니, 분리되지 않은 설계들이 서로를 구속해 초기 설계 부담이 과도하게 커졌다.
2. **추적 가능성에 대한 오해**가 문제를 키웠다.  
   - 단일 데이터로 저장·분석을 해결하려 했지만 **MSA 현실(다수 서비스/인스턴스)** 을 간과했다.  
   - 목적 분리가 안 되자 어떤 DB를 쓰든 **용량·인덱스 부담**이 폭증하는 구조가 됐다.  
   - Observability는 반복 질의로 원인과 위치를 좁히는 과정인데, 이를 **로그 자체와 혼합**해 구현하려 했다.
3. **데이터 특성의 난이도**  
   - **고 카디널리티**(계속 늘어나는 값) + **고 디멘셔널리티**(다양한 인덱스 축)  
   - 사실상 “모든 컬럼 인덱싱”이 필요해지고, 저장 장치와 운영 복잡도가 급격히 상승한다.
4. **단일 DB 집착**  
   - 고 카디널/고 디멘셔널 데이터를 한 곳에서 다루려다 보니 더 어려워졌다.  
   - 분리 대신 단일 스토어(예: 뷰 확장)로 덮으려 했던 판단이 과했다.

---

## 4. 앞으로의 개선 방향
1. **로그 스키마의 디멘셔널리티를 줄이고**, 우선 **로그 저장**을 완성한다.  
2. 메트릭 관련 코드는 **비활성**으로 유지(삭제는 아님).  
3. Observability 관련 요소는 **현 단계에서 제거**하고, **로그 저장 경량 경로**만 남긴다.

---

## 5. 마무리
이번 회고의 핵심은 **스코프를 좁히고, 로그 저장 경량 경로를 먼저 완성**하겠다는 전환이다.  
Observability는 이후 단계에서 **별도 경로**로 설계·도입할 예정이며, 지금은 **단순하고 빠른 로그 저장·조회**에 집중한다.
