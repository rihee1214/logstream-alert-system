## 전체 개요

- **발생 일자:** 2025-05-27
- **제목:** MVP 기반 전략으로 개발 방향 전환
- **상세 내용:**
	- 기존에는 전체 시스템을 완전하게 구현하려는 접근을 취해왔으나, 시간이 너무 부족하고 유지 관리 포인트가 많아져, 
	  현재는 **"최소한 동작하는 구조"에 집중하고, 정책/실패/예외 처리는 후속 작업으로 미루는 방식**으로 전환함.
	- 현재 리소스와 시간에 비해 설계와 고민이 깊어 복잡성이 급격히 증가하고 있음.
	- 문서화만 해두고, 실제 구현은 나중에 필요한 시점에 진행하는 것으로 전략 조정.
- **현재 상태:**
	- 전체 구조는 동작 가능한 MVP 수준을 우선 구현 중.
	- 정책, 실패 처리, 고급 분기 처리, 최적화 등은 `docs/todo/` 및 `issues/` 폴더에 기록만 진행.
	- 테스트는 성공 경로에 한정.
- **대응 방안:**
	- 각 모듈별 "후속 적용이 필요한 정책/기능 목록"을 문서화하여 추후 우선순위에 따라 처리.
	- 추후 포트폴리오 발표나 정리 시, 해당 문서들을 개선 이력 및 설계 의도로 활용할 수 있도록 정리 유지.
- **참고 링크:** n/a

## 🚨 업그레이드 주의사항 (Upgrade Cautions)

- **업그레이드시 신경 써야하는 대상**
	1. 모든 컴포넌트의 설계
	     - 각 컴포넌트는 현재 작성된 구조로부터 추후 기능/정책을 삽입하기 쉬운 방향으로 설계되어야 함
	     - 공통 인터페이스, 적절한 추상화, 유연한 경계(모듈 간 의존성 등)를 고려해야 함
	  2. 문서 최신화의 어려움
	     - 문서 내용은 작성 시점의 구현을 반영해야 하며, 기능 개발 이후에 일괄 작성하는 방식은 불완전해질 가능성이 큼
	     - 정책 추가, 모듈 구조 변화, 내부 흐름 변경 등으로 인해 문서가 빠르게 낙후되기 쉬움
	     - 실제 구현 흐름을 반영하며 구조화된 문서 갱신 체계를 마련해야 함

- **업그레이드시 발생 가능한 문제**
	1. 컴포넌트 설계는 MVP 단계부터 "변경이 쉬운 구조"로 설계되어야 한다
		 - 추가될 **정책**을 구조적으로 반영하기 쉬운 기반이어야 함 (예: 스케줄러 정책, span ID 생성 정책 등)
	     - 모든 기능을 MVP에서 구현할 수 없기 때문에, 이후 확장이 가능한 설계를 차악의 형태라도 고려해야 함
	     - 최소한의 윤곽만 잡아두고, 정책/옵션 추가는 기능 중심이 아니라 구조 중심으로 삽입할 수 있어야 함
	2. 문서 관리 및 최신화는 “구현 완료 후 작성”이 아니라 “수시로 반영되는 방식”이 되어야 한다
	     - MVP 이후의 기능 추가 시 기존 문서가 **전면 수정**되거나 **쓸모없어질 위험**이 큼
	     - 따라서 문서 자체도 **유지보수가 가능한 구조**로 작성되어야 하며,
	     - 코드와 동기화가 가능한 수준의 참조 구조(예: `docs/guide`, `docs/policy`, `issues/`)가 선행되어야 함

- **업그레이드시 신경 써야 하는 부분**
	1. 유연성 있는 설계 적용
	     - 현재 존재하지 않는 정책이 나중에 도입되었을 때 **어떤 영역이 변경될지**에 대한 인지가 필요
	     - 이를 바탕으로 구조에 여유 공간을 두거나, 정책 삽입 포인트를 명확히 정의해두어야 함
	     - 예: WebClient 필터 전략, TraceContext 구조, 스케줄러 재시도 정책 등
	2. 문서 관리를 위한 추가 개선사항
		 - MVP에서 제외된 각 개발 요소(정책, 실패 처리 등)에 대해서는 각 컴포넌트 단위로 설계 문서 혹은 보류 문서 형태로 남겨야 함
	     - 단순 task 리스트가 아닌, 최소한의 설계 기준과 도입 의도까지 담긴 구조화된 문서를 지향해야 함
	     - 문서가 기능을 설명하는 것이 아니라 “기능이 왜 그렇게 생겼는지”를 설명할 수 있어야 함
